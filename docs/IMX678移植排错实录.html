Phase 01

01 模板:imx515 是完美双胞胎

SDK 无 imx678,但 sony_imx515 与之近亲(Sony 8MP / 4-lane / RAW12 / 3840×2160)。以它为骨架:

cd $SRC/mpp/cbb/isp/user/sensor/hi3519dv500
cp -r sony_imx515 sony_imx678
cd sony_imx678
# 文件名 + 符号全部 imx515→imx678（g_sns_imx515_obj→g_sns_imx678_obj 等）
for f in *; do mv "$f" "${f/imx515/imx678}"; done
sed -i 's/imx515/imx678/g; s/IMX515/IMX678/g' *

关键认识:sed 只改了符号名,寄存器地址和数值仍是 imx515 的 —— 这埋下后面 cmos 地址错、Bayer 错、OB 错等一连串雷。父目录 Makefile 自动发现新 sensor 目录。

Phase 03

03 反汇编抠寄存器表

初始化寄存器序列编在原厂 libsns_imx678.so。反汇编抽取:

aarch64-...-objdump -d libsns_imx678.so > imx678.asm
# 每次写寄存器: mov w2,#data ; mov w1,#addr ; bl imx678_write_register
awk '/mov\tw1, #0x/{if(match($0,/#0x[0-9a-f]+/))a=substr($0,RSTART+1,RLENGTH-1)}
     /mov\tw2, #0x/{if(match($0,/#0x[0-9a-f]+/))d=substr($0,RSTART+1,RLENGTH-1)}
     /bl.*imx678_write_register/{gsub(":","",$1);printf"%s %s %s\n",$1,a,d}' imx678.asm

线性 8M init 入口 0x3eb0,调用链 0x3eb0(直接写5条) → 0x3a30(INCK/VMAX 47条) → 0x1890(大块 pathA 323条) → 0x3e00(1条) → 释放,共 376 条写,搬进 imx678_sensor_ctl.c 的 imx678_linear_8m_init()。

⚠ path A/B 岔路

0x1890 有 cmp w1,#1; b.eq 靠全局标志的运行时分叉:pathA=323 条(首次完整 init),pathB=44 条(已初始化重入)。首次上电走 A。抠错 = 缺一大半。

⚠ 别直接用 blob

原厂 .so 是 MPP V1.0.1.1 / 2023-11-23 编的,与 SDK V1.0.2.0 的 ot_isp_sns_obj 结构布局不一致 → 3A 回调注册栈溢出段错误。必须把寄存器数值搬进 imx515-源码编的 ABI 原生驱动,而非用二进制。

🔬 科普

这 ~300 个寄存器到底在配什么?

绝大多数不是"功能开关",而是 Sony 出厂标定的模拟前端魔法数字。按作用分几类:

  • 时钟 / PLL(0x3014 INCK、0x3015 DATARATE):告诉传感器输入时钟多少、把 MIPI 输出锁到哪个速率——全片最要命的两个。
  • 模式 / 画幅(0x301b 合并模式、0x3022/23 AD/MD 位深、0x3040 lane 数):决定分辨率、12bit、4-lane。
  • 帧时序(HMAX 0x302c、VMAX 0x3028):一行多少个时钟、一帧多少行 → 决定帧率(74.25M÷HMAX÷VMAX)。
  • 曝光 / 增益(SHR 0x3050、gain 0x3070):快门和放大,由 ISP 的 AE 每帧动态写。
  • 模拟读出 / ADC / 校正(0x3Axx–0x47xx 那一大片,占了 ~300 条的绝大部分):像素放大器偏置、比较器阈值、ADC 斜坡、逐行读出时序、黑电平、列间串扰校正…… 这些几乎无法逐条读懂,是 Sony 针对这颗芯片的物理特性调出来的。

为什么一条都不能少?缺了模拟读出那片寄存器,传感器输出的原始帧本身就是坏的(噪声、错位、时序乱)——MIPI 收到也是垃圾。这正是必须从原厂固件完整搬、不能自己凑的原因:这些数字没有文档、也不该由我们发明。

Phase 04 · Root Cause

04 大 Boss:看不见的时钟(MCLK)

寄存器搬进去了,却依旧解不开:MIPI 四 lane 有流、phy 频率乱漂(222/296/446)、CRC/对齐爆表、vc_frmnum=0。三个版本的寄存器表全一个乱法。

从运行中的原厂固件直接读寄存器

让板子从 flash 启动原厂固件(正干净出图),telnet 进去用它的 i2ctransfer 读运行中寄存器:

# 读寄存器 0xNNNN: 高字节 低字节 r1
i2ctransfer -y 3 w2@0x1a 0x30 0x14 r1   # → 0x01 (INCK_SEL)
i2ctransfer -y 3 w2@0x1a 0x30 0x15 r1   # → 0x04 (DATARATE)

🔴 Root Cause · MCLK

寄存器逐字节相同,输出速率却差 2 倍 → 唯一变量是 SoC 喂给传感器的主时钟。传感器被 INCK_SEL=0x01 告知"输入=37.125MHz",而我们这颗 SoC 实际喂 74.25MHz → 内部 PLL 输出翻倍 → D-PHY 锁不住 → 满屏乱码。原厂那颗 SoC 喂的正是 37.125,故 0x01 对它对;我们照抄就翻车。之前读到的 296MHz 是 PHY 没锁时的噪声,真值就是原厂那个稳定的 148MHz。

修复:告诉传感器真实的时钟

因为我们的 MCLK 是 74.25MHz,INCK_SEL 必须设 0x00(74.25),而不是照抄原厂的 0x01。

sony_imx678/imx678_sensor_ctl.c · imx678_linear_8m_init() 时钟根因
- imx678_write_register(vi_pipe, 0x3014, 0x1);  /* INCK 37.125 (照抄原厂,错) */
+ imx678_write_register(vi_pipe, 0x3014, 0x0);  /* INCK 74.25 = 本板 SoC 实际时钟 */
✅ 活体验证(不重编)

i2ctransfer -y 3 w3@0x1a 0x30 0x14 0x00 + 重启传感器 → phy 296→148MHz、vc0=3840×2180 单通道、CRC 全 0、VI int_cnt 开始递增。固化后干净启动:mipi_rx 与原厂逐字节一致。

* VMAX 会被 cmos 的 AE 按目标帧率覆写;74.25M/(HMAX1100×VMAX2250)=30fps,原厂 VMAX2700=25fps。

🔬 科普

为什么一个时钟位能让整幅图崩掉?

MIPI(CSI-2)是串行高速链路:传感器把像素数据在几条差分线上以每秒几亿位的速度串着发出去。接收端的 D-PHY 必须先"锁"住发送端的时钟节拍,才能在正确的时刻采样每一个比特。

传感器内部有个 PLL(锁相环)倍频器,输出速率 = 函数(输入时钟 INCK, 倍频设置)。你通过 INCK_SEL 告诉它"我的输入是 37.125MHz",它就按这个基准去倍频。可我们这颗 SoC 实际喂的是 74.25MHz(2 倍) → PLL 按错的基准算 → 输出速率翻倍 → 接收端 PHY 的采样节拍全对不上 → 每个字节都读错 → CRC 全爆、满屏乱码。

这也解释了那个诡异现象:寄存器逐字节相同、结果却天差地别。因为"输入时钟到底多少"是 SoC 硬件决定的,不写在传感器寄存器里——只有把我们和原厂放一起对比,这个隐藏变量才现形。

Phase 05

05 帧收到了却全丢:OB 高度

MIPI 干净后:int_cnt 涨、send_cnt=0 / lost_cnt≈int_cnt,编码器一路 get venc stream time out。原厂 img_h=2180(2160 有效 + 20 行光学黑 OB),我们 =2184(OB=24)。传感器实发 2180,MIPI RX 却等 2184 → 帧凑不齐 → 全丢。

sample_comm_vi.c · sample_comm_vi_get_mipi_attr() 画幅对齐传感器
- ob_height = OB_HEIGHT_END;   /* = 24 → img_h 2184 */
+ ob_height = 20;              /* img_h = 2160+20 = 2180，与传感器实发一致 */
⚠ 连环坑:ISP 裁剪要一致

改 OB=20 后 ISP 报 isp_pub_wnd_rect_attr_check Invalid image y:24 height:2160——裁剪窗口另一处还是 y=24,24+2160=2184 > 2180 越界。OB 高度与 ISP 裁剪偏移必须相等。

sample_comm_isp.c · g_isp_pub_attr_imx515_mipi_8m_30fps 裁剪 y 对齐 OB
  static ot_isp_pub_attr g_isp_pub_attr_imx515_mipi_8m_30fps = {
-     {0, 24, 3840, 2160},   /* {x, y=OB偏移, w, h} */
+     {0, 20, 3840, 2160},

三处对齐(MIPI 2180 / ISP y=20 / 传感器 2180)→ 帧不丢,编出 33MB 有效 H.265 4K(NAL 头 00 00 00 01 40 01=VPS)+ 1080p H.264。

Phase 06

06 发紫的真凶:Bayer 排列

画面结构完美但整体品红。干净对照:同一 IR-Cut 滤镜、同场景 → 原厂正常,我们的紫。 证明 100% 软件问题,与红外/硬件无关。

🔴 Root Cause · Bayer/CFA

ISP 靠 Bayer 排列(RGGB/BGGR/GRBG/GBRG)重建颜色。我们的 pub attr 写的是 imx515 的 GBRG,而 IMX678 基准(无翻转,0x3030=0)是 RGGB。排列错位 → R/B 错位 → 系统性偏品红/紫。

sample_comm_isp.c · g_isp_pub_attr_imx515_mipi_8m_30fps 颜色
- OT_ISP_BAYER_GBRG,
+ OT_ISP_BAYER_RGGB,

一行,重编 → 紫色消失,颜色全对。

🔬 科普

传感器是"色盲",颜色是拼出来的

传感器像素本身只能测光的强弱,分不出颜色。要出彩色,得在像素上盖一层马赛克滤色片(CFA / Bayer):每个像素只透红或绿或蓝,按 2×2 的 RGGB 图案不断重复。所以传感器直接输出的原始帧(RAW)是一张马赛克灰度图。

ISP 再做去马赛克(demosaic):根据每个像素的颜色 + 周围邻居,插值算出它缺的另外两个通道,还原成每像素完整 RGB。前提是 ISP 得知道这层马赛克的排列顺序。

我们告诉它是 GBRG,实际是 RGGB → 它把红当蓝、蓝当红去插值 → 整幅图系统性地把颜色搬错位 = 品红/紫。改对一个枚举,ISP 就用对了排列,颜色瞬间归位。陷阱:传感器做镜像/翻转会让这个图案相位跟着变(RGGB→翻转→BGGR),所以设 Bayer 得连翻转状态一起算。

⚠ 陷阱

mirror/flip 会改变有效 Bayer 相位(RGGB 经 180°翻转→BGGR)。设 Bayer 须连翻转状态一起算。另:画面结构清晰 + CRC 全 0 + 检测宽度正好 3840,已排除 RAW12 打包/位深问题——偏色只可能在色彩平面。

Phase 08

08 网页打不开:一个字段引发的「连接重置」

传感器出图后做了个 MJPEG 网页预览(mode 13)。用户报:页面根本打不开、浏览器报「连接重置」,但直接访问 /snap 每次都能出图。服务器明明是活的。

🔴 Root Cause · RST

HTML 响应没带 Content-Length(只有 Connection: close)→ 浏览器要一直读到连接关闭为止。而代码 read() 只读了 299 字节请求就 write()+close(),socket 收缓冲里还压着没读完的浏览器请求头(几百字节~数KB) → 内核对「有未读数据就 close」的响应是发 RST 而非 FIN → 浏览器读 HTML 读到一半被重置。
/snap 带了 Content-Length,浏览器读够就算完成,RST 来得再晚也不影响——所以只有它「看起来正常」。

两处都要修
sample_venc.c · web 模块 RST 根因
// ① HTML 响应补上 Content-Length(g_web_html 改成纯 body,不再内嵌 HTTP 头)
+ snprintf(hh, sizeof(hh), "HTTP/1.0 200 OK\r\nContent-Type: text/html; charset=utf-8\r\n"
+          "Content-Length: %d\r\nConnection: close\r\n\r\n", (int)strlen(g_web_html));

// ② 关闭前排空未读请求数据,让内核发 FIN 而不是 RST
+ static void web_close(int fd) {
+     char tmp[512]; struct timeval tv = {0, 200000};
+     setsockopt(fd, SOL_SOCKET, SO_RCVTIMEO, &tv, sizeof(tv));
+     shutdown(fd, SHUT_WR);
+     while (read(fd, tmp, sizeof(tmp)) > 0) { }   /* drain */
+     close(fd);
+ }
✅ 不用板子就能验证

这段逻辑与 MPP 无关,纯 HTTP 收发框架 → 抽出来在 x86 上 gcc 编译独立跑,用 python raw socket 测:GET / → 200 + Content-Length + 完整 body + 无 reset;灌 4KB 超大请求头(模拟真实浏览器,超服务器读缓冲)→ 依然无 reset。真机复测一致。
心法:能脱离硬件验证的部分,就别占用宝贵的上板时间。

顺手把预览做成真流

老版实时预览是 <img src=/snap> + JS onload→setTimeout→改src 自刷新,时序不稳、卡顿。改成浏览器原生吃的 MJPEG 连续流(所有 IP 摄像机的标准招):

// multipart/x-mixed-replace: 一条长连接里不断吐 JPEG
Content-Type: multipart/x-mixed-replace; boundary=frm
--frm\r\nContent-Type: image/jpeg\r\nContent-Length: N\r\n\r\n<jpeg>

架构关键:VENC 的 get_stream 是单消费者,多个 HTTP 客户端不能各拉各的。做法是 1 个 reader 线程取流→最新帧存 g_web_jpeg[mutex],N 个 client 线程共享读——顺带根治了老版长连接卡死。实测 5 秒 72 帧 = 14.4fps(设计 usleep(66000)≈15fps,吻合)。

Phase 09 · Root Cause

09 二号 Boss:「图像叠在一起,慢慢变淡」

网页能看直播了,但用户一句话点出新问题:「像是图像叠在一起 慢慢的变淡」。抓帧确认——运动的手臂拖出多层半透明残影,整幅画面发灰发朦、像蒙了层纱。而同一颗摄像头、同一张桌子,原厂固件拍出来锐利通透。硬件无罪,是我们的 ISP。

从症状到嫌疑人

「运动物体留下逐渐变淡的残影」= 典型的时域降噪(3DNR)把连续多帧混在一起。但为什么 3DNR 会疯成这样?笔记里其实早埋了一条线索——「gain 地址存疑:cmos 用 0x3090,原厂/will127534 用 0x3070」,当时判断「不阻碍 decode,先留」。它咬人了。

i2c 活体对质
# 直接读跑着的传感器
0x3070/71 (IMX678 真 ANALOG_GAIN) → 0x00 0x00 = 0   # 从来没被写过!
0x3090/91 (我们在写的地址)       → 0xf0 0x00 = 240 # 240×0.3dB = 72dB 顶格
0x3050-52 (SHR 曝光)            → 8            # 正好顶在代码下限
🔴 Root Cause · GAIN 地址(imx515 残留)

和当初的 VMAX 0x3024→0x3028 是同一类漏网之鱼——整套 cmos 抄自 imx515,GAIN_PGC 留着 imx515 的 0x3090,而 IMX678 的模拟增益在 0x3070。
于是 AE 的增益指令全部写进了一个无效地址:房间暗 → AE 想加增益 → 写 0x3090 → 石沉大海,真增益永远是 0 → 画面还是暗 → AE 只剩一招:把曝光往死里拉 → SHR 撞到下限 min(max(value,8),…) = ≈48ms 超长曝光 → 运动即拖影。

为什么一个地址同时治好「重影」和「发朦」?

因为 ISP 的整条下游流水线是「增益感知」的。ISP 以为增益开到了 240(72dB),就按「超高增益 = 噪点爆炸」来处理:3DNR 开到最猛(多帧混合 → 残影)、黑电平/DRC/色调曲线全按高增益补偿(→ 发灰发朦)。而传感器实际增益是 0——ISP 的认知和物理现实差了 72dB,整条链全错。

sony_imx678/imx678_cmos.c 重影 + 发朦 根因
- #define  IMX678_GAIN_PGC_L    0x3090    /* imx515 残留 */
- #define  IMX678_GAIN_PGC_H    0x3091
+ #define  IMX678_GAIN_PGC_L    0x3070    /* IMX678 真 ANALOG_GAIN (11bit: 低8 + 高3) */
+ #define  IMX678_GAIN_PGC_H    0x3071
✅ 结果

重编重跑后 i2c 实读:0x3070 = 0x08 → 0x0a 随 AE 实时跳动(拿回控制权),0x3090 回落到出厂默认。抓帧对照:人脸/眼镜/手指/瓶子标签全部清晰、黑衣服是纯黑、肤色自然、零重影。

🔬 心法

「存疑但不阻碍,先留」的债,迟早要还

这个地址在笔记里被标记过两次「存疑」,每次都因为「当前不阻塞」被跳过。它没让链路断——它让链路带病工作,伪装成一个看起来完全不相干的画质问题(重影)。
教训:「寄存器地址写错」不一定报错,它可能只是让某个反馈环路默默失效。AE 是个闭环——写坏它的执行端,它会用另一个旋钮(曝光)拼命补偿,于是故障从「增益不对」变形成「运动拖影」。顺着症状找因果链时,要敢于怀疑那些「早就标记过但一直没管」的东西。

Phase 10

10 自制 RTSP:440 行,一次点亮

SDK 不带 RTSP,live555 太重。既然 VENC 已经吐标准 H.265/H.264 裸流,自己写一个极简 RTSP 更干净(musl 的 pthread 内建在 libc,连 -lpthread 都不用)。

要素做法
RTSP 控制(TCP 554)thread-per-connection,实现 OPTIONS/DESCRIBE/SETUP/PLAY/TEARDOWN
DESCRIBE按 URL 路径 /main|/sub 选流,回 SDP(含从码流抓的 sprop-vps/sps/pps base64)
SETUP解析 client_port=,用 getpeername 拿客户端 IP 当 RTP 目的地
RTP 打包每流一个线程:get_stream→按 annex-b start code 切 NAL→单NAL≤1400直发,超了 FU 分片
H.265 / H.264FU type49(2字节头) / FU-A type28(1字节头);marker 打在 is_frame_end 的最后 NAL
✅ 真机第一次跑就通

ffprobe rtsp://板/main → hevc 3840×2160 25fps;/sub → h264 1920×1080 25fps。抓帧解码正确(4K 帧 632KB、锐利)。SDP、FU 分片重组、会话表全对。

🔬 科普

RTSP 本身不传视频

RTSP 只是个「遥控器」协议:DESCRIBE 问「你有什么流」(回 SDP)、SETUP 商量端口、PLAY 开始。真正扛视频的是 RTP——把 H.265 裸流按 NAL 切片、打上时间戳+序号,一包一包发。大帧超过 MTU 就 FU 分片,接收端按序号重组。
这也是「浏览器为什么放不了 RTSP」的答案:浏览器没有 RTP 栈。所以原厂网页走的是另一条路——WebSocket 推流 + ffmpeg.wasm 在浏览器里软解(它 webs/ws/ 里那个 2MB 的 wasm 就是干这个的)。

⚠ 已知缺口:只实现 UDP(RTP/AVP unicast)。客户端若请求 TCP interleaved,SETUP 仍回 UDP 的 Transport 行 → Nonmatching transport。VLC 走 TCP 时需在设置里取消「RTP over RTSP (TCP)」,或后续补 interleaved=0-1 + RTP 包加 4 字节 $ 头。

板子没有 SD 卡槽、eMMC 空焊 → 唯一存储就是板载 32MB SPI NOR。目标:脱离 NFS/VM/网络,插电自启。

🐞 坑 1 · rugzip 不认我们的包

原厂 bootcmd 用私有命令 rugzip 解压 mtd3。我们照着 SDK 的 kernel_compress.sh 造了逐字段同构的 gziphead 包([压缩后大小4B][原始大小4B]["gziphead"8B]+gzip流),连 XFL 字节都对齐成 0x00,rugzip 依旧 decompress file failed(原因至今不明)。
绕开它:我们的 gzip 流被标准 gunzip -t 验证完全有效 → 改用 U-Boot 自带的标准 unzip,一次成功。

# 新 bootcmd(0x50000010 = 跳过我们那 16 字节 gziphead 头)
sf probe 0; sf read 0x40010000 0x80000 0x10000;
sf read 0x50000000 0x90000 0x600000; unzip 0x50000010 0x44000000;
ipcboot bl31 0x40010000; ipcboot uimgfdt 0x44000000
🐞 坑 2 · No working init found

内核起来了、jffs2 根也挂上了(VFS: Mounted root … on device 31:4),却挨个试 /sbin/init、/bin/sh 全「跑不起来」→ panic。
因为打包 jffs2 时手动枚举目录 for D in bin sbin etc lib64,漏了 /lib —— busybox 的解释器正是 /lib/ld-musl-aarch64.so.1(→/lib64/libc.so)。加载器没了,busybox 就是块砖:文件都在,但一个也执行不了。

修法与心法:别手动枚举,整根 rsync 只排除大块头(--exclude=/root/*** /usr/lib/*** /opt/***),并逐项自检 lib/ld-musl、bin/sh、sbin/init、/init、/linuxrc。
⚠ 自检还有个陷阱:readlink -f 解析绝对符号链接时是按宿主机的根解析的,会给出假象(显示 /usr/lib64/libc.so 那种根本不在包里的路径)。要用脚本在 staging 内部模拟解析才作数。

安全边界:为什么这不是赌博

用户在爱尔兰、没有编程器——一旦砖了没硬件可救。但这套操作可逆,靠一条铁律:

🛟 永不写 mtd0(U-Boot) / mtd2(bl31)

只要 U-Boot 活着,板子就永远能救:它不依赖任何其他分区就能起到串口命令行,然后 tftp + sf write 刷回任意分区。我们所有写入偏移 ≥ 0x90000,距 U-Boot 末尾(0x70000)隔着 9MB。
交叉验证偏移表:七个分区的「偏移算出的大小」与「dump 出来的备份文件实际字节数」逐个精确吻合——偏移不是猜的。
写前必校验:U-Boot 没有 md5sum 就用 crc32 <addr> <len> 对一遍再 sf write。TFTP 重传再凶也无所谓——错一个 bit,CRC 立刻露馅。

✅ 成果:整机只读,天生耐拔电

/ = jffs2(ro) · /opt = squashfs(ro) · /tmp = tmpfs(RAM) → 没有一处可写文件系统 → 随便拔电,不可能损坏、不用 fsck。这正是 IPC 该有的设计。

Phase 12 · Root Cause

12 隐藏 Boss:整晚的网络鬼故事

这一晚一半的时间耗在网络上:VM 时通时断、TFTP 从 1.5MB/s 崩到 83KB/s 满屏 T、板子「ping 得通」却连不上……看起来像三四个独立故障,其实是两个根因。

🔴 根因 A · 板子直连网口 = 整个网段的命门

板子直连电脑网口(无交换机),而 VM 的 ens37 桥接在这块网卡上。于是:
板子一崩/一重启/一断电 → 主机网口失去链路对端 → Windows 把 192.168.1.2 标记 Deprecated、撤掉 1.x 路由 → VM(1.50) 瞬间失联,发往 1.x 的包改走 WiFi 默认路由 → ISP 回 Destination net unreachable。

⚠ 附带陷阱:Windows 的 ping 会骗人

ping 收到 ISP 的「不可达」应答也算成功(exit 0) → 脚本里的 ping && echo 通 多次误判「板子活着」,把排查带进沟里。判断可达性必须看应答内容,不能只看 exit code。

🔴 根因 B · 第二块桥接网卡 = 帧重复

VM 上多挂了一块桥接 WiFi 的 ens33 → 同一个帧被投递进 VM 两次。tcpdump 铁证:同一个 ICMP 回复相隔 1 微秒出现两遍(真的网络环路要绕一圈,至少差毫秒 → 说明是本地重复投递,不是环路)。
为什么专杀 TFTP:TFTP 是 UDP、发一块等一个 ACK 的死板 lockstep,重复 ACK 会触发经典的「魔法师学徒综合症」——服务器被骗着重发、越滚越多 → 速度雪崩。
nmcli device disconnect ens33 后 TFTP 立刻从 83KB/s 回到 1.5MB/s。⚠ NetworkManager 会把它自动拉回来(实测复发),要在 VMware 设置里移除那块适配器才根治。

✅ 心法

开发期的板子天天崩,就别让主机网络的死活依赖它。两个免费解法:①给 VM 加一块 host-only 网卡当管理口(纯虚拟、不依赖物理链路 → 板子随便崩,SSH 永远在);②找个闲置旧路由器,LAN 口当交换机(板子和电脑各插一个)→ 主机链路永远 UP。
更普适的一条:当「好几个看似无关的故障」同时发作时,先怀疑它们共享同一个物理根因。

Phase 13

13 出图之后:从"传感器通了"到"一台成品相机"

出图+固化只是起点。此后 sample_venc.c 一路长成了整台网络相机的唯一载体(单文件 ~5.4k 行):4K H265 /main + 1080p H264 /sub 双 RTSP、720p MJPEG 网页预览、4K 抓拍下载、IMX678 寄存器实时 I2C 直读、GPIO 监视、ISP 图像调节(持久化)、设 IP/网络、MMZ 内存显示、网页终端 /exec、dropbear SSH —— 全部 auth-gated,配置存在 param(mtd6)分区里跨重启保留。每一轮都用同一套"/tmp 冒烟 → 后台 mtdwrite → 回读 md5 → 重启验证"的固化法上 flash。

4.3" DSI 屏:默认关,才敢固化未测的代码

要给相机加一块本地 Waveshare 800×480 DSI 屏(走 SoC 的 VO + mipi_tx)。但屏在国内、人在欧洲 —— 代码写好了却没硬件可测。破法是:集成进固件但默认关闭(scr_en=0),开屏只在网页手动启用时才碰 VO/mipi_tx/i2c → 未接屏也能安全烧进 flash,零副作用。已固化并重启验证:屏关闭时整机行为与之前逐字节一致,0 条 [scr] 日志。

✅ 一个源喂两个消费者:屏不额外占 VPSS 通道

4 个 VPSS 物理通道已全被 venc 占满(4K/1080p/720p/4K抓拍)。但海思 ss_mpi_sys_bind 是按"目的地"键控的 —— 同一个 VPSS 源可以同时喂给 venc 和 VO。于是把 chn2(720p,本就在产帧)再 bind 到 VO 不破坏原有的 →venc2 绑定,VO 内部自己缩放到 800×480。省掉了一路多余的 VPSS。

🐞 坑 · Makefile 是 wildcard *.c

venc/Makefile 把目录里每个 .c 都当成一个独立可执行目标。所以屏驱动不能作为第二个 .c 丢进去(会去 build 一个没有 main 的 dsi_panel_43 而报错)→ 屏代码全部内联进 sample_venc.c,原 dsi_panel_43.c 只留作参考。
另:那份"照规格写"的驱动逐字段拿 SDK 头核对才敢编 —— sample_comm_vpss_bind_vo 的签名是 (grp,chn,vo_layer,vo_chn) 不是注释里猜的 (vo_dev,vo_layer);pixel_clk 单位是 Hz(27777000)不是 KHz;ot_vo_sync_info 的 18 个字段顺序按 ot_common_vo_dev.h 重排。屏的真实出图仍待回国接 J5 实测。

🛟 远程固化的安全网

没有编程器、人板隔着一块大陆,固化全靠三条:①永不写 U-Boot/kernel/rootfs(只动 mtd5 user + mtd6 param);②rootfs 里的 S90tcpsvd 在 S99cam 之前起一个 23 端口后门 shell —— 它跑在 rootfs 上,不依赖 /opt,所以就算把 /opt 卸载/刷坏,shell 还在,能重刷;③写完先 dd 回读比 md5,一致才 reboot。mtdwrite 擦 21MB 要约 1 分多钟,必须后台跑,别用短超时前台把它掐断。
